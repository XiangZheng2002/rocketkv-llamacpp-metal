# RocketKV Metal MVP: preliminary implementation report

## Result

The native CPU reference and GPU-resident Metal implementation run Llama-3.2-3B-Instruct Q4 end to end. The bounded 2K/4K evaluation completed, with saved Full-KV/RocketKV results, component timestamps and accuracy checks. **This implementation did not outperform Full-KV decode in this MVP.** Selection, gather and execution overhead outweighed the benefit of attending fewer values at these sizes. This is a result for this prototype and machine, not a final RocketKV break-even point.

Measured October 3, 2026, 02:35:07-02:46:22 UTC (October 2, 22:35:07-22:46:22 EDT). Machine: Apple M2 MacBook Air, 16 GiB unified memory, macOS 26.7, Xcode 26.2. Baseline llama.cpp revision: `99b95488cac0f00ce3f05af113a8c1e287753f87`. The 2,019,377,696-byte model is `Llama-3.2-3B-Instruct-Q4_K_M.gguf`; its SHA-256 and pinned download command are in `README.md` and the result provenance.

All implementation, tests, scripts and final results are under `Code/llama.cpp`. No weights or datasets were converted, no 8B model was downloaded/run, and no LongBench/RULER full suite was executed. No commit or upstream submission was made. The external reference source remains unchanged.

The implementation keeps the original RoPE-transformed keys and absolute logical positions. Each layer/KV head can retain a different prompt subset, shared by its associated query heads. The final prefill still computes dense causal attention. Decode attends selected real K/V, not min/max summaries. Page metadata changes only for the newly appended key. Query values, metadata, selections, K/V and attention output are not read back to the CPU during selection/decode.

The reference code has a non-commercial research/evaluation license. `NOTICE` and a complete `LICENSE.NVIDIA` are retained, and the new RocketKV-specific implementation is labeled accordingly. This is not an MIT-only upstream-ready contribution.

## Correctness evidence

Four deterministic fixtures were generated by importing official `gpt-fast/rocket.py` at `63637c8eb4b06b5eb83cd687723b0eeb19f48f65`. The independent C++ reference and the native CPU/Metal graphs agree on retained indices, grouped scores, pooling, compaction, Kmin/Kmax, top-r, approximate page/token scores, top-k, gathered K/V and attention outputs. Exact-TopK is tested only as a fixture oracle.

Both CTest targets pass. Seventeen `test-backend-ops -b MTL0 -o ROCKETKV` cases pass against CPU, including deterministic tied top-k at 1, 17, 128, 1025 and 8192 entries. Incremental tests cover F16/F32, page sizes 1/2/3/5, every partially filled page, masked padding and zero queries. Floating tolerances are documented in the README; indices, stored F16 values and metadata require exact agreement.

Real-model smoke runs with 96 prompt tokens, budget 32, window 8, and prefill chunks 17 and 7 verify observations spanning batch boundaries. CPU and Metal emit identical smoke token IDs. Unsupported serialization, nonconsecutive positions and mutated caches are rejected. The unchanged completion CLI's output is byte-identical to the output captured before implementation.

Three short prompts were compared with Full-KV at both budgets: all six comparisons match the complete 32-token greedy sequence. These requests fit their budget and correctly use the dense fast path. For every long synthetic/passkey pair, the exact prompt IDs and prefill-produced first token agree between modes; later sparse outputs may differ.

The Python harness tests and the repository's pinned `ty` checker pass. The optional generator reproduces the checked-in JSON byte for byte, with bytecode writes disabled in the external reference tree. RPC compatibility code passes a standalone C++ syntax check without enabling or starting an RPC service.

## Uninstrumented MVP performance

Same Q4 weights, F16 K/V, 28 layers, batch-one greedy decode, 512-token prefill chunks, 32 emitted tokens (31 decode calls). Each configuration has one unmeasured warm-up and three measured repetitions. Means below use only measured repetitions; TPOT uncertainty is sample standard deviation.

| Prompt | Mode | Budget | Engine TTFT (ms) | Request TTFT (ms) | TPOT (ms/token) | Total decode (ms) |
|---|---|---|---|---|---|---|
| 2048 | Full-KV | - | 5488.32 | 5573.03 | 27.975 +/- 0.896 | 867.23 |
| 2048 | RocketKV | 256 | 6185.92 | 6291.88 | 41.074 +/- 1.547 | 1273.28 |
| 2048 | RocketKV | 512 | 6095.95 | 6177.26 | 47.532 +/- 1.580 | 1473.49 |
| 4096 | Full-KV | - | 13147.21 | 13277.76 | 32.565 +/- 3.023 | 1009.50 |
| 4096 | RocketKV | 256 | 11636.17 | 11776.86 | 40.097 +/- 0.263 | 1243.02 |
| 4096 | RocketKV | 512 | 13271.14 | 13416.01 | 47.034 +/- 3.198 | 1458.06 |

TPOT is 46.8%/69.9% higher at 2K and 23.1%/44.4% higher at 4K for budgets 256/512. These are slowdowns, not speedups. The lower observed 4K/budget-256 TTFT must not be interpreted as prefill acceleration: prefill still does dense attention plus extra RocketKV work, and the small, shared-machine samples are noisy.

Engine TTFT includes prefill and obtaining the first greedy token. Request TTFT additionally includes context creation/initialization, but not one-time model loading, tokenization or Python/process setup. TPOT sums decode plus greedy sampling/logit synchronization; output formatting and OS-memory sampling are excluded. Full request/process timing is retained separately. Fixed-length generation continues after EOG; that protocol is identical across modes, but their generated token sequences are not forced to remain identical.

The one MVP Q8_0 K/V sanity comparison at 2K has TTFT 8143.54 ms, TPOT 35.168 ms and a 133.88 MiB KV allocation. It has one warm-up and one measured repetition; it is not a statistical quantized-KV comparison. During initial unmodified-baseline calibration, comma-separated cache types also produced two mixed-F16/Q8 diagnostic rows; they are archived but excluded from the MVP tables and conclusions.

## Component profiling

These are **separate instrumented runs**, also one warm-up plus three repetitions. M2 stage-boundary timestamp sampling requires additional encoder boundaries and disabled fusion, so component times explain this instrumented graph; they are not an additive breakdown of the uninstrumented wall times above.

| Prompt / budget | Stage 1 total (ms/request) | Stage 2 selection + metadata + indexing + gather (ms/request) | Exact sparse attention (ms/request) | Selection overhead (ms/decode step) | Exact attention (ms/decode step) |
|---|---|---|---|---|---|
| 2048 / 256 | 91.14 | 389.39 | 21.75 | 12.56 | 0.70 |
| 2048 / 512 | 123.21 | 715.38 | 27.71 | 23.08 | 0.89 |
| 4096 / 256 | 168.59 | 556.43 | 26.01 | 17.95 | 0.84 |
| 4096 / 512 | 236.17 | 856.64 | 31.73 | 27.63 | 1.02 |

Stage 1 includes maintaining the observation ring during prefill. All required subcomponents are available in `profiles.json`, not just the aggregated columns. Each measured request records exactly 28 metadata constructions and 868 metadata updates / exact sparse-attention layer calls (`28 * 31`). Profiling fails rather than accepting missing GPU layers or incomplete timestamp samples.

In the instrumented 4K/budget-512 request, gather costs 464.88 ms, top-k selection 215.55 ms, approximate scoring/group softmax 124.35 ms, query top-r work 24.13 ms, index/KV writes 21.63 ms, incremental metadata 6.10 ms, and exact sparse attention 31.73 ms. Gather includes the existing GGML F16-to-F32 gather and conversion back to F16. Those conversions and deterministic sorting are demonstrated optimization candidates; no speculative fusion or additional optimization/evaluation sweep was run after completing this MVP.

macOS physical footprint is an OS accounting metric and does not include all file-backed model mappings; RSS and declared tensor allocation are also shown to avoid interpreting the small footprint number as total model memory. Samples occur at chunk/token boundaries, not continuously. Small RSS/footprint differences are not evidence of RocketKV memory savings. Declared allocation is higher for RocketKV because the full cache remains and auxiliary buffers are added.

System swap already contained 3099.81 MiB before the MVP and reached 4226.81 MiB by its end. The OS-reported free-memory percentage ranged from 45% to 55%; `pmset` reported no recorded thermal/performance warning. Other applications were not stopped. These observations prevent clean attribution of paging and timing variation to one mode. No maximum-context or end-to-end peak-memory improvement is claimed.

## Artifacts and remaining limits

`results/rocketkv-mvp/summary.json`, `performance.csv`, `profiles.json`, `accuracy.json`, `provenance.json` and `raw/*.json` contain the machine-readable result set, exact commands/prompts/output tokens, source/model hashes and before/after machine state. `validation.json` and the correctness logs record final checks. `evaluated-implementation.patch` preserves the exact runtime/source snapshot used for the matrix; its fingerprint is `f3e1283fec4b8383f4095128eb89e5887b3286843dccaa072ac5da01aa1c5230`.

After measurement, integration/validation cleanup added RPC enum compatibility and transport rejection, public-header/license installation and attribution packaging, explicit logging for a null statistics-query context, and Python typing fixes that reproduce identical fixtures/results. No attention algorithm, Metal kernel or benchmark timing code changed. The archived patch avoids mislabeling the measured source as the later cleanup state.

The retained workspace is approximately 2.2 GiB, including the single Q4 model and one approximately 111 MiB release build; result data is only a few MiB. It stays well below the 10-15 GiB target and 20 GiB ceiling.

Known limits: full preallocation and compute reservation; explicit prompt/decode length; single sequence, single turn and no cache/session reuse; CPU/Metal-only, Llama-only, F16 RocketKV K/V; stable sorting bounded to 8192 entries; no speculative decoding/training; diagnostic timestamp overhead; three repetitions on a shared machine; synthetic accuracy only. Compressed physical allocation and cheaper gather/selection remain distinct future milestones.

`future-full-evaluation.json` and the JSONL adapters prepare 8B/full-suite work without executing it. The 16K/32K configurations are explicitly marked as requiring implementation extensions and a new memory budget. Full quantized combinations, larger budgets/generation sweeps, ablations, bandwidth counters, energy and maximum-context claims remain deferred.
